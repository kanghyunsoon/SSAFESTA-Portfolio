# 문제 해결 기록

Unity 클라이언트와 전용 서버를 맡아 AI 에이전트와 구현·수정을 진행했습니다. 아래에는 문제를 확인한 과정과 측정 조건을 적었습니다.

## 1. 25번째 이후 접속이 끝나지 않은 문제

Unity Transport 수신 큐를 늘려 초기 접속을 완료한 뒤, 동기화 설정을 조정해 전송량을 줄였습니다.

봇 25기가 붙은 서버는 접속을 승인했지만 클라이언트는 `IsConnectedClient=false`에 머물렀고 플레이어가 생성되지 않았습니다. 서버의 `Approved client` 로그와 클라이언트 상태를 대조하니 클라이언트에서 다음 경고가 반복됐습니다.

```text
Insufficient space in receive queue
Receive queue is full, some packets could be dropped (128)
```

1. `UnityTransport.MaxPacketQueueSize`를 128에서 1,024로 올렸습니다.
2. `NetworkTransform`에서 사용하지 않는 X/Z 회전 동기화를 껐습니다.
3. 위치 임계값을 `0.001 → 0.05`, 회전 임계값을 `0.01 → 1`로 바꿨습니다.
4. Half Float를 시험했지만 수신량이 `3,290 → 3,816 KB/s`로 16% 늘어 되돌렸습니다.

| 항목 | 전 | 후 |
|---|---:|---:|
| 수신 큐 | 128 | 1,024 |
| 초기 플레이어 생성 | 실패 | 26명 확인 |
| 클라이언트 프레임 | 측정 불가 | 43.4 FPS |

접속 시험은 한 PC에서 Dedicated Server, Unity Editor, 봇 25기를 함께 실행했습니다. 서버 CPU는 28~55%, 메모리는 295MB였습니다. 초기 렌더링 후 접속이 끊겨 다시 로그를 남겼고, 후속 시험에서는 접속 92.8초 뒤 끊김과 최대 20.5초의 에디터 프레임 지연을 확인했습니다. 26명은 초기 생성·렌더링 결과이며 장시간 접속 유지 결과는 아닙니다.

트래픽은 별도로 11명(봇 10기) 조건에서 비교했습니다. 동기화 축과 임계값을 조정한 뒤 클라이언트 수신량이 `4,529 → 3,290~3,505 KB/s`로 약 25% 줄었습니다. Half Float는 같은 시험에서 수신량이 늘어 적용하지 않았습니다.

근거: [KHS 트러블슈팅 T-220](../KHS/25_트러블슈팅.md), [최적화 기록 §8](../KHS/28_최적화_기법_정리.md)

## 2. WebGL 프레임 저하의 원인을 다시 나눈 과정

오클루전 설정과 스킨메시 결합으로 드로우콜을 줄였습니다. 다만 드로우콜 감소율만큼 프레임이 변하지 않아 측정 방법도 다시 확인했습니다.

WebGL에서 아바타 40기를 표시했을 때 25.7 FPS가 측정됐습니다. 처음에는 픽셀 처리를 의심했지만 캔버스를 `1920×1200 → 640×400`으로 낮춰 픽셀 수를 9분의 1로 만들어도 프레임은 12%만 나아졌습니다.

부스 벽과 천장에 오클루더 설정이 빠져 있어 뒤쪽 물체도 그려지고 있었습니다. 설정 후 부스 내부 시점에서 `UnityStats.drawCalls`가 `1,088 → 231`로 줄었습니다. 이 값은 특정 시점의 비교이며 월드 전체에서 항상 같은 비율로 줄어든다는 뜻은 아닙니다.

아바타는 같은 재질과 골격을 쓰는 신체 파츠를 결합해 `SkinnedMeshRenderer`를 `11 → 7`로 줄였습니다. 빌드에서 메시를 읽지 못해 결합이 실패하는 문제는 대상 FBX 2개에 Read/Write를 켜고 `isReadable`을 확인하도록 수정했습니다.

이후 WebGL Development Build의 11층 전시실에서 아바타 40기를 모두 화면에 담아 비교했습니다. 캔버스는 1920×1200이며, 각 조건의 4초 평균을 한 번씩 측정한 값입니다.

| 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 드로우콜 | 990 | 676 |
| 평균 프레임 시간 | 38.8ms | 35.8ms |

드로우콜은 31.7% 줄었지만 프레임 시간은 7.7% 줄어, 아틀라스 작업에 앞서 다른 비용을 확인하기로 했습니다. 이 비교만으로 스키닝과 Animator 각각의 비용을 확정하지는 않았습니다.

Animator 갱신 주기 조절은 처음에 프레임 시간 17% 감소로 기록했다가 철회했습니다. 워밍업 중 자연스럽게 프레임이 줄어드는 것을 효과로 읽었기 때문입니다. 조건을 번갈아 다시 측정한 차이는 0.09ms로, 같은 조건의 회차별 변동보다 작았습니다. 이후에는 스폰·로드 직후 30초를 제외하고 조건별로 최소 3회씩 번갈아 측정하도록 기준을 바꿨습니다.

근거: [최적화 기록 §3-1·§10·§15·§16](../KHS/28_최적화_기법_정리.md), [T-211 측정 정정](../KHS/25_트러블슈팅.md)

## 3. 아바타 카탈로그 메모리

아바타 텍스처의 최대 해상도를 낮춰 카탈로그 메모리를 `490.3 → 194.3MB`로 줄였습니다. 조사한 텍스처는 124종이고, 이 중 50종이 2048px였습니다. 서로 다른 외형을 표시하면 카탈로그의 여러 텍스처를 함께 읽게 되므로 Import 설정의 최대 크기를 1024px로 제한했습니다.

UI 이미지는 표시 크기에 맞춰 따로 조정했습니다. 188×156px로 보이는 목록 이미지는 256px로, 여러 얼굴이 들어 있는 시트는 1024px로 설정하고 변경 전후 캡처를 비교했습니다.

| 항목 | 전 | 후 |
|---|---:|---:|
| 카탈로그 런타임 메모리 | 490.3MB | 194.3MB |
| 총 픽셀 | 259.8M | 102.5M |
| 2048px 텍스처 | 50종 | 0종 |
| UI 텍스처 | 65.70MB | 4.32MB |
| WebGL 빌드 총량 | 138.78MB | 130.79MB |

UI 에셋의 감소량과 내려받는 빌드의 감소량은 다릅니다. 빌드에는 압축이 적용되므로 최종 다운로드 크기는 약 8MB 줄었습니다.

근거: [최적화 기록 §14·§14-1](../KHS/28_최적화_기법_정리.md), [측정 자료](../KHS/measurements/README.md)

## 4. SDD와 AI 에이전트를 통합 검증에 사용한 방식

파트 테스트를 통과한 코드도 Unity와 연결해 실행한 뒤 완료 처리하도록 바꿨습니다. AI가 작성한 코드에서 각 파트의 문서 차이와 WebGL 실행 조건을 놓치는 일이 있었기 때문입니다.

게임 개발에 AI 에이전트를 적용한 첫 팀 프로젝트라 구현 전에 약 일주일 동안 기능 범위, 담당자, 완료 조건, API 계약, 코드와 Git 규칙을 팀원들과 맞췄습니다. 저는 규약을 주제별로 나누고 인덱스를 두어 작업에 필요한 문서를 찾도록 했습니다. 작업 중 생긴 문제는 MCP를 통해 트러블 문서와 Jira·GitLab 이슈로 연결했습니다.

통합 과정에서는 다음 차이를 확인했습니다.

- Published Layout 경로: `/layout/published`와 `/layouts/published`
- 오브젝트 식별자: `id`와 `objectId`
- 에디터에서 통과했지만 WebGL 빌드에서 읽을 수 없던 런타임 메시
- 숨은 브라우저 탭에서 `requestAnimationFrame`이 멈추며 끊긴 연결

AI와 문서·코드의 차이 및 수정할 파일을 확인했습니다. Unity 쪽 요청 경로와 DTO를 Spring 계약에 맞춘 뒤, 응답을 읽어 부스를 생성하고 Unity–React 브리지와 전용 서버가 연결되는 흐름을 실행했습니다. 그 결과를 작업 문서에 남기고 완료 여부를 판단했습니다.
