# 문제 해결 기록

이 문서는 제가 맡은 Unity Client와 Dedicated Server에서 재현하고 측정한 내용만 정리합니다. 팀 전체 기능 수나 다른 파트의 구현을 제 결과로 포함하지 않았습니다.

## 1. 25번째 이후 접속이 끝나지 않은 문제

### 결론

서버 용량보다 Unity Transport의 수신 큐가 먼저 찼습니다. 큐를 늘려 초기 접속을 통과시킨 뒤 전송량을 줄였습니다.

### 문제

봇 25기가 붙은 서버는 새 클라이언트를 승인했지만 클라이언트는 `IsConnectedClient=false`에 머물렀고 플레이어가 생성되지 않았습니다. 같은 시점 서버는 CPU 28~55%, 메모리 295MB를 사용했습니다.

### 확인

서버의 `Approved client` 로그와 클라이언트 상태를 대조했습니다. 서버 거부가 아니라 클라이언트 수신 큐에서 다음 로그가 반복됐습니다.

```text
Insufficient space in receive queue
Receive queue is full, some packets could be dropped (128)
```

### 조치

1. `UnityTransport.MaxPacketQueueSize`를 128에서 1,024로 올렸습니다.
2. `NetworkTransform`에서 사용하지 않는 X/Z 회전 동기화를 껐습니다.
3. 위치 임계값을 `0.001 → 0.05`, 회전 임계값을 `0.01 → 1`로 바꿨습니다.
4. Half Float를 시험했지만 수신량이 `3,290 → 3,816 KB/s`로 16% 늘어 되돌렸습니다.

### 결과

| 항목 | 전 | 후 |
|---|---:|---:|
| 수신 큐 | 128 | 1,024 |
| 초기 플레이어 생성 | 실패 | 26명 확인 |
| 클라이언트 프레임 | 측정 불가 | 43.4 FPS |
| 11인 수신량 | 4,529 KB/s | 3,290~3,505 KB/s |

이 시험은 한 PC에서 Dedicated Server, Unity Editor, 봇 25기를 함께 실행했습니다. 약 20초 뒤 끊김은 20.5초 에디터 스톨로 하트비트가 멈춘 결과였습니다. 따라서 26명은 초기 생성·렌더링 결과이며 장기 유지 결과가 아닙니다. 40명은 슬롯 목표일 뿐 실측 결과가 아닙니다.

근거: [KHS 트러블슈팅 T-220](../KHS/25_트러블슈팅.md), [최적화 기록 §8](../KHS/28_최적화_기법_정리.md)

## 2. WebGL 프레임 저하의 원인을 다시 나눈 과정

### 결론

해상도만 낮춰서는 해결되지 않았습니다. 씬 드로우콜, 아바타 드로우콜, 스키닝, Animator 갱신을 따로 측정했습니다.

### 문제

WebGL에서 아바타 40기를 표시했을 때 25.7 FPS가 측정됐습니다. 처음에는 GPU 픽셀 처리를 의심했지만 캔버스를 `1920×1200 → 640×400`으로 낮춰 픽셀 수를 9분의 1로 만들어도 프레임은 12%만 나아졌습니다.

### 조치와 판단 변경

- 부스 외벽을 오클루더로 사용해 축제 구역 드로우콜을 `1,088 → 231`로 줄였습니다.
- 같은 재질과 골격을 쓰는 신체 파츠를 결합해 아바타당 `SkinnedMeshRenderer`를 `11 → 7`로 줄였습니다. 빌드에서 메시가 읽히지 않는 문제는 필요한 FBX 2개에만 Read/Write를 켜서 해결했습니다.
- 이후 별도 A/B에서 드로우콜을 `990 → 676`으로 31.7% 줄였지만 프레임 시간은 `38.8 → 35.8ms`, 7.7%만 줄었습니다. 드로우콜만으로 병목을 설명할 수 없어 가설을 수정했습니다.
- 스키닝과 Animator 갱신을 분리해 측정했습니다. 거리에 따라 원격 Animator를 4프레임마다 갱신하자 분산 배치 조건에서 프레임 시간이 `15.55 → 12.30~13.58ms`로 17% 줄었습니다.

### 남은 조건

근거리 아바타 40기가 모이면 모두 근거리 단계라 Animator LOD 효과가 없습니다. 스킨메시 결합의 WebGL 재측정도 기록 당시 남아 있었습니다. README에는 예상 드로우콜을 결과처럼 쓰지 않았습니다.

근거: [최적화 기록 §10·§15·§16](../KHS/28_최적화_기법_정리.md)

## 3. 아바타 카탈로그 메모리

### 결론

아틀라스를 만들기 전에 텍스처의 실제 표시 크기와 런타임 메모리를 조사해 해상도부터 줄였습니다.

### 문제

고유 텍스처 124종은 259.8M 픽셀, 런타임 490.3MB였고 2048px 텍스처가 50종이었습니다. 40명이 다른 외형을 쓰면 카탈로그가 한꺼번에 로드될 수 있었습니다.

### 조치

- 텍스처 Import 설정 126건의 최대 크기를 1024px로 제한했습니다.
- 무늬 텍스처와 얼굴 시트는 표시 품질을 확인하며 별도 상한을 적용했습니다.
- UI 목록에서 188×156px로 보이는 이미지는 256px 기준으로 다시 설정했습니다.
- 변경 전후 캡처를 비교하고 아틀라스는 비용 대비 프레임 이득이 작아 진행하지 않았습니다.

### 결과

| 항목 | 전 | 후 |
|---|---:|---:|
| 카탈로그 런타임 메모리 | 490.3MB | 194.3MB |
| 총 픽셀 | 259.8M | 102.5M |
| 2048px 텍스처 | 50종 | 0종 |
| UI 텍스처 | 65.70MB | 4.32MB |
| WebGL 빌드 총량 | 138.78MB | 130.79MB |

근거: [최적화 기록 §14·§14-1](../KHS/28_최적화_기법_정리.md), [측정 자료](../KHS/measurements/README.md)

## 4. SDD와 AI 에이전트를 통합 검증에 사용한 방식

### 결론

AI가 만든 코드는 파트 안의 조건은 따랐지만 파트 사이 변경과 WebGL 실행 조건까지 확인하지 못했습니다. 완료 기준을 문서 작성과 코드 병합에서 종단 실행으로 바꿨습니다.

### 진행 방식

게임 개발에 AI 에이전트를 적용한 첫 팀 프로젝트라 구현 전에 약 일주일 동안 기능 범위, 담당자, 완료 조건, API 계약, 코드와 Git 규칙을 문서로 맞췄습니다. 규약은 주제별로 나누고 인덱스에서 필요한 문서만 찾도록 했습니다. 작업 중 생긴 문제는 트러블 문서와 Jira·GitLab 이슈에 연결했습니다.

### 통합에서 찾은 문제

- Published Layout 경로: `/layout/published`와 `/layouts/published`
- 오브젝트 식별자: `id`와 `objectId`
- 에디터에서 통과했지만 WebGL 빌드에서 읽을 수 없던 런타임 메시
- 숨은 브라우저 탭에서 `requestAnimationFrame`이 멈추며 끊긴 연결

### 바꾼 기준

Spring 응답, Unity DTO 역직렬화, 런타임 오브젝트 생성, Unity–React 브리지, 전용 서버 로그를 순서대로 확인했습니다. AI는 문서와 코드의 차이, 누락 필드, 영향 파일을 찾는 데 사용했습니다. 완료 여부는 실행 결과와 측정값으로 정했습니다.
